# H.A.R.D — Delivery Outcomes

## 1. Homepage, workspace routes and navigation — Open
- `/` is a polished public homepage in the supplied H.A.R.D design language, with accessible cards/links to patient, doctor, front desk, pharmacy, lab, provider-admin and platform-admin entry points. It explains the product and keeps fictional demo access distinct from real sign-in. It does not expose protected patient or clinical data.
- `/login` provides real Supabase sign-in; `/signup` provides email/password and Google OAuth signup. `/patient`, `/doctor`, `/front-desk`, `/pharmacy`, `/lab`, `/provider-admin` and `/admin` route an authenticated, authorized user to that role’s `/overview` page. A platform admin may access every workspace page; other users need the assigned role. Unauthenticated users are sent to login; users with the wrong assigned role receive an access-denied result.
- Provide nested pages: patient `/overview`, `/timeline`, `/prescriptions`, `/reports`, `/expenses`, `/providers`, `/billing`, `/settings`; doctor `/overview`, `/patients`, `/patients/[patientId]`, `/prescriptions/new`, `/prescriptions/[prescriptionId]`; front desk `/overview`, `/patients/new`, `/patients/[patientId]`, `/collections`; pharmacy `/overview`, `/resolve`, `/dispenses`, `/bills`; lab `/overview`, `/reports/new`, `/reports/[reportId]`; provider admin `/overview`, `/staff`, `/ledger`; admin `/overview`, `/providers`, `/config`, `/audit`, `/users`.
- Keep `/verify/lab/[token]` as a minimal public verification page with no patient identifiers/clinical details. `/rx/resolve` accepts only an opaque pharmacy token/code and enforces single-prescription access. Keep `/manus-routes.json` complete and synchronized with every static and dynamic page route.
- Use the supplied reference: compact icon rail, warm-white canvas, pastel amber/rose/aqua metrics, wide chart, rounded charcoal summary panel, teal actions, and responsive patient/pharmacy mobile navigation.

## 2. Supabase authentication, profile roles and demo separation — Open
- Integrate Supabase Auth for real email/password sign-in and sign-out plus email/password and Google OAuth signup using server/client SSR helpers and refreshed secure session cookies. A database-side auth-user trigger assigns every new account the `patient` application role, regardless of user metadata or submitted form fields. Signup UI does not offer a role selector. Only an active `platform_admin` may grant/revoke any other role or provider membership; provider admins cannot grant roles. Google OAuth requires the Google provider/client credentials and callback allowlist to be configured in Supabase and Google.
- Preserve the existing demo-only role switcher and fictional demo records as a visibly separate mode; demo personas and local state do not gain access to Supabase user data. Simulated OTP, payments, messaging and role changes remain explicitly labelled as simulations.
- Do not place secrets in Git, browser code, URL parameters, logs or chat. The only browser Supabase values are the project URL and public anon/publishable key; never ship a service-role key to the client. Use separate development/test and production configuration.
- Use synthetic records and files only until a separate compliance-ready production-data design is approved. Do not import real CNICs, patient records or clinical files as part of this prototype work.

## 3. Provider onboarding and front-desk registration — In progress
- Provider registers name, type, license number, address, contact and document; status is Pending. Platform admin can approve or reject with a note. Provider admins may request staff access, but only a platform admin can assign application roles or provider membership.
- Front desk searches by CNIC or phone to prevent duplicates; CNIC is unique. A duplicate CNIC is rejected. If no patient exists, registration captures name, DOB, gender, CNIC, phone, blood group, height, weight and emergency contact.
- CNIC is the patient identifier; generate a Health ID such as `HARD-000123`, link the patient to the registering provider, and create a registration invoice. Mark the invoice paid using mocked cash/card/wallet payment; simulate delivery of login credentials. Record the CNIC desk check as `desk_checked`; NADRA verification is out of scope.
- A paid invoice collected by a provider creates exactly one revenue split and two ledger entries whose amounts sum exactly to the invoice total. Use the configured provider-share percentage and display the split confirmation.
- Returning-patient search uses CNIC or Health ID without making a duplicate. Providers can see only an actively linked patient; unlinked access requires simulated patient approval/OTP or the logged emergency override where provided.

## 4. Doctor history and digital prescriptions — In progress
- Doctor opens a linked patient and sees history: visits, prescriptions, reports and allergies; patient history view includes recent visits, active prescriptions, allergies and latest reports. Include visit complaint, diagnosis, vitals, notes and an optional sensitive flag.
- Provide medicine search over a seeded catalogue of about 100 medicines (generic and brand names), saved prescription templates, and repeat-last-prescription. Prescription items include medicine, strength, dose, frequency, duration and quantity.
- On Issue, create a unique prescription ID (UUID and readable code such as `RX-7F3K-92QD`), an opaque short-code/QR token containing no Health ID, CNIC, name or medical data, expiry (default 30 days), maximum fills (default 1), and a printable prescription layout with QR. Simulate patient notification. Add the consultation cost automatically or allow it to be recorded by front desk.
- Provider-issued records are system-tagged Verified with provider, doctor and timestamp. Issued records are never deleted. An amendment creates a new version, cancels the old QR, and retains the old prescription record.
- Keep prescription creation streamlined and make expiry, fill count, and the configured short-code behavior visible in the demo; prototype-only token/OTP controls must not be represented as production signing or rate limiting.

## 5. Pharmacy resolve, OTP dispense, and attached bill — In progress
- The pharmacy reaches prescription data only through QR scan or typed code. It has no patient search, patient list, Health ID, CNIC, history, or access to any other patient endpoint/record.
- On resolve, show only one prescription’s verified doctor/clinic, date, medicine names and quantities, status, fills remaining, and at most the patient’s first name and age range. Log each resolve and make it visible in the patient access log.
- Expired, cancelled, or fully dispensed prescriptions return a clear status without medicine details. Do not allow dispensing after expiry, cancellation, or beyond configured maximum fills. Simulate the patient OTP requirement before marking dispensed; record fill items, pharmacy, pharmacist, time and OTP state. Support partly filled and dispensed states.
- Pharmacy keeps its own billing software and attaches a bill to that prescription: bill number, line items, total, and optional file placeholder. Generate linked Medicine cost items; update prescription status and simulate patient notification.
- Use large touch targets and a mobile-friendly scan/code entry surface. Manual code entry remains available if camera scan is unavailable.

## 6. Patient dashboard, timeline, expenses, and access — In progress
- Patient dashboard is mobile-first and displays patient name, Health ID and storage meter; spending this month and year, budget remaining; category, provider and monthly trend charts; recent activity; active prescription QR access; storage/outstanding-invoice alerts.
- In response to the supplied dashboard reference, style patient Overview with a compact icon-only desktop rail; warm-white overview canvas; three soft amber/rose/aqua financial metric cards with restrained trend accents; a wide monthly activity chart; and a rounded charcoal summary panel containing patient profile facts, budget/storage status and the active prescription action. Keep the layout responsive and preserve H.A.R.D’s financial clarity and every existing navigation/workflow action.
- Show Overview, Timeline, Prescriptions, Reports, Expenses, Providers & Access, Billing and Settings sections. Timeline combines visits, prescriptions, reports, bills and expenses; supports type/date/provider filters and keyword search. Clinical items have the immutable source badge and sensitive-flagged records are hidden from everyone except patient and treating doctor (court later).
- Show spending totals for month/year/all-time, category/provider summaries, trend, biggest expenses and average per visit. Costs include PKR amount, category (Consultation, Test, Medicine, Procedure, Admission, Other), provider/date, payment status, source, linked entity, and optional `covered_amount` defaulting to zero. Costs are automatically created from issued documents and attached bills; patient-entered expenses are Self-reported. Update totals without a manual refresh after in-demo actions.
- Include monthly budget alerts at 80% and 100%, CSV/PDF statement export, linked provider list, revoke-provider-link control, and patient-visible access log. Log every non-patient read/write, including doctor read, pharmacy resolve, emergency and court access where present.

## 7. Plans, invoices, storage, revenue ledgers, and provider accounting — In progress
- Include Base, Plus and Pro storage plans with configurable quota and yearly price. Defaults: registration PKR 500 including year one and 1 GB; renewal PKR 400/year; Plus 5 GB at PKR 1,000/year; Pro 20 GB at PKR 2,500/year; provider share 30%; storage alert 80%; prescription validity 30 days/max one fill; court access 30 days; emergency access 24 hours.
- Show registration, renewal, upgrade and outstanding invoices; simulate mock payment method and receipt number. Provider-collected paid invoices create split and platform/provider ledger entries that reconcile to the invoice. Provider earnings ledger has running balance and Pending/Settled payout status, with settlement controlled by admin.
- Show storage usage based on demo file sizes. At 80%, alert patient and linked providers. At 100%, block new uploads while reading remains allowed. Upgrade invoice can be paid by patient or provider at desk and triggers a revenue split. Unpaid renewal never blocks reading and appears as an outstanding invoice at the next front-desk visit.
- Provide provider cost/accounting view with cost/revenue per visit, test type and medicine; monthly totals and top items. Provider admin KPIs include patients registered, documents issued, fees collected, share earned (pending/settled), outstanding invoices, staff, and earnings ledger.

## 8. Lab report creation and public verification — In progress
- Lab tech creates a report for a linked patient with test type, date, structured result values, notes and optional file placeholder; generate a verification QR/link and related cost item.
- Verification page shows issuing lab, date, test, “genuine and unchanged” demo status and a report hash. Log provider reads. Patient receives an in-app notification and a simulated WhatsApp/SMS message preview containing the link; do not send real messages.

## 9. Patient AI-document review and confirmation — In progress
- Patient can upload/select a fake older PDF/photo document (lab report, prescription or bill). Prototype extraction may be a mocked response only; it does not prove authenticity and must not use or expose an external AI credential.
- Show a review screen with document type, date, provider, extracted items and quantities/amounts/values/units, total, confidence and warnings. Patient must review/edit and confirm before saving, with sanity checks for totals and duplicate provider/date/total. Saved records are labeled AI-read, patient-confirmed and retain a local/original-file placeholder. Handwritten/Urdu extraction uncertainty is explained. Identity verification and NADRA are out of scope.

## 10. Provider admin, platform admin, audit, and notifications — In progress
- Provider admin sees provider KPIs, staff-access requests and earnings ledger. Platform admin has an audited user directory and can assign/revoke application roles and provider membership; only platform admin can grant roles. A platform admin can open any configured role workspace/page and has all H.A.R.D application permissions, including access to clinical content, all organizations and all record views/actions. Every cross-role/admin read and write must be authorized in database code and included in the audit log with actor, action, resource and time. This app role does not grant Supabase project-owner privileges.
- Audit/access event types distinguish normal read, pharmacy resolve, emergency override and court access. Patient is notified in-demo about pharmacy resolves, dispense, report ready, new bills, outstanding invoices, storage thresholds, budget alerts, link requests and access events.
- Court and sponsor views, emergency override, Urdu labels and simulated messaging remain stretch items and must not displace the four core journeys. If an emergency override is shown, require a reason, simulate 24-hour expiry, log it and notify patient. Court access is read-only, requires a case/order approval mock, defaults to 30 days, is logged and notifies the patient.

## 11. Supabase schema, RLS and persistent demo/test data — Open
- Use Supabase Auth/Postgres for real account identity and persistent application data; keep the role-switcher prototype isolated from authenticated accounts. Use versioned migrations and typed schema for profiles/roles, providers and staff, patients, active provider links, visits, prescriptions/items/versions, pharmacy resolves/dispenses, lab reports, costs/bills, invoices, ledger splits, storage plans, and audit events.
- Enforce record access with Postgres RLS and narrow server-side operations. Patients can read/write only permitted fields on their own records; provider staff can read only actively linked patients in their organization; pharmacy users can resolve only one opaque prescription token and receive the restricted payload; active platform administrators can use a separately checked and audited override to access any app data. RLS and route protection are both required; client-side visibility is not authorization.
- Make audit records append-only for application roles and log relevant non-patient reads and writes. Keep data provenance immutable. Use a private storage bucket for synthetic test files only, with scoped access and upload type/size limits; never expose a public bucket for clinical documents.
- Use only synthetic seed data and a separate development/test project. Do not run test writes or migrations against production. Do not import real CNICs, patient records or clinical files without a separately approved compliance/security plan.

## 12. Application security and privacy — Open
- Protect every role route on the server and database; users cannot self-assign roles and only platform admins can grant/revoke roles. Apply secure refreshed cookies compatible with HTTPS Preview/Vercel. Validate all inputs server-side, use least privilege, rate-limit sign-in and token resolution, keep opaque tokens single-purpose/expiring, and avoid logging credentials, tokens, CNICs or clinical content.
- Keep Supabase service-role keys out of browser bundles, source files and logs; prefer public anon/publishable key plus correct RLS. Store any required protected values only in secure deployment settings. Apply security headers without blocking the cross-site Preview iframe; sanitize content and constrain file type/size.
- Platform admin has all H.A.R.D application permissions and cross-workspace access, with all admin reads/writes recorded in the audit log; pharmacy users still have no patient search/history; public verification exposes no patient identity. Prototype notifications, payments, OTP and document extraction remain explicitly simulated unless separately integrated and authorized.
- Document that this prototype is not a certified healthcare system and does not establish regulatory compliance; obtain legal/privacy/security review before using real clinical records.
